<Callout variant="important">
  Agent Control and New Relic Control are **generally available** for Kubernetes. Support for Linux and Windows hosts is in **public preview** program, pursuant to our [pre-release policies](/docs/licenses/license-information/referenced-policies/new-relic-pre-release-policy).
</Callout>

Agent Control is a lightweight supervisor you install once per Kubernetes cluster or host. It connects to [Fleet Control](/docs/new-relic-control/fleet-control/overview) and manages every aspect of your agents' lifecycle from there — deploying new agents, applying configuration changes, performing rolling upgrades, and reporting health status — without requiring you to touch individual machines again.

<Callout variant="tip" title="Key behaviors">
  - **Starts without agents:** Agent Control installs as a lightweight supervisor with no managed agents running by default. You define which agents to deploy through Fleet Control after installation.
  - **Remote install and upgrade on Linux and Windows:** On Linux and Windows hosts, you can install, configure, and upgrade agents remotely through Fleet Control — no manual intervention required on each host.
  - **No automatic agent migration:** Agent Control does not automatically migrate or replace existing agent installations. Uninstall any existing agents before installing Agent Control, then manage them through Fleet Control. See [Migrate existing instrumentation](/docs/new-relic-control/agent-control/reinstrumentation).
  - **No additional cost:** The supervisor itself doesn't push any telemetry to New Relic. Ingest cost depends only on the instrumentation enabled in your managed agents.
</Callout>

## The problem Agent Control solves

Managing instrumentation at scale is labor intensive and error prone. When you operate tens, hundreds, or thousands of Kubernetes clusters and hosts, the gap between the agent version you intend to run and the version actually running tends to grow. Configuration drift accumulates. A single change — bumping an agent version, adjusting a scrape interval, rotating a license key — requires touching each machine individually or maintaining complex automation outside of New Relic.

Agent Control changes this model. Instead of pushing changes to machines, you declare the desired state of your instrumentation once in Fleet Control. Agent Control, running on each cluster or host, continuously reconciles reality against that desired state and reports back. Your entire agent fleet converges on the correct configuration, version, and health — automatically.

The core workflow is straightforward:

1. **Install Agent Control** on each Kubernetes cluster or host using the guided install in the New Relic UI. This installs only the lightweight supervisor — no agents are deployed yet.
2. **Agent Control connects to Fleet Control** over an encrypted, authenticated channel using the [OpAMP](https://github.com/open-telemetry/opamp-spec) protocol. The connection is outbound-only from your environment.
3. **Deploy agents from Fleet Control.** Define which agents to run, their versions, and their configuration in the Fleet Control UI. Agent Control receives this desired state and deploys the agents.
4. **Manage everything from Fleet Control.** Upgrade agents, update configuration, and monitor health across your entire fleet — all from the New Relic UI, without touching individual machines.

## What Agent Control handles for you

Agent Control addresses five distinct responsibilities. Each maps to a dedicated section of the documentation.

### 1. Deploy and manage agents at scale

Whether you manage five clusters or five hundred Linux hosts, Agent Control eliminates per-machine operations. Define the desired agent state once in Fleet Control — which agents to run, at which versions, with which configuration — and Agent Control ensures every machine in your fleet converges to that state. Any deviation (a failed upgrade, a missing agent, a config that was manually changed) is detected and corrected automatically, without your involvement.

Agent Control performs non-disruptive rolling updates: the new agent version is verified healthy before the old one is removed. No scripts to coordinate, no SSH, no drift.

On Kubernetes, Agent Control uses [Flux](https://fluxcd.io/) as its delivery engine, managing agents as Helm releases through HelmRelease and HelmRepository CRDs. On Linux and Windows, agents run as native system services supervised by Agent Control.

→ [Install Agent Control](/docs/new-relic-control/agent-control/setup) · [Supported agent types](/docs/new-relic-control/agent-control/agent-types)

### 2. Manage configurations from a single source

Agent settings — scrape intervals, log paths, resource limits, integration toggles — flow from Fleet Control to every cluster and host in your fleet over a secure, outbound-only channel. Change a setting in Fleet Control once; Agent Control applies it everywhere.

The two-layer model:

- **Remote configuration** (from Fleet Control) is always authoritative — it overrides any local settings.
- **Local configuration** (`values.yaml` on Kubernetes, `config.yaml` on Linux/Windows) is the fallback when no remote configuration has been defined.

Agent Control integrates with [HashiCorp Vault](https://www.vaultproject.io/) and Kubernetes Secrets so credentials are injected at runtime — license keys and tokens never need to live in config files.

### 3. Understand what's deployed and how healthy it is

Agent Control continuously monitors every agent it manages and reports health, version, and configuration state back to Fleet Control. From the Fleet Control UI you can see, across your entire fleet, which agents are running, the version in use on each cluster or host, whether they're healthy, and what configuration they received — without connecting to individual machines.

For direct, on-machine inspection, Agent Control exposes a local HTTP `/status` endpoint that returns the live health of the supervisor and every managed agent. This is your entry point when you need to diagnose a specific cluster or host, or verify that a change was applied correctly.

→ [Agent health and fleet visibility](/docs/new-relic-control/agent-control/monitoring)

### 4. Manage Agent Control itself

Agent Control is itself a managed service. On Kubernetes, you can update the Agent Control supervisor version directly from Fleet Control — no direct cluster access required. On Linux and Windows, Agent Control is packaged as a standard system service and upgraded through your OS package manager or by re-running the install script. Start, stop, and restart commands use standard OS tools (`systemctl` or PowerShell).

→ [Upgrades and lifecycle](/docs/new-relic-control/agent-control/upgrading)

### Security

All Agent Control capabilities operate under a consistent security model:

- **Outbound-only connectivity.** Agent Control initiates all connections to Fleet Control. Your environment does not need to accept inbound traffic.
- **Encrypted, authenticated communication.** All Fleet Control traffic uses mutual TLS with rotating credentials.
- **Secrets never in config files.** Credentials are injected at runtime from Vault or Kubernetes Secrets.
- **Minimum required permissions.** On Kubernetes, Agent Control manages only Flux CRDs — not cluster-admin operations. On Linux and Windows, elevated privileges are scoped to declared lifecycle tasks only.

### Multi-environment support

Agent Control runs wherever your workloads run. A single Fleet Control deployment manages all environments from one UI.

| Environment | GA / Preview | Managed agents |
| :--- | :--- | :--- |
| Kubernetes | ✅ Generally Available | Infrastructure, NRDOT, Fluent Bit, Prometheus, eBPF |
| Linux hosts | Public Preview | Infrastructure, NRDOT |
| Windows hosts | Public Preview | Infrastructure, NRDOT (experimental) |

For a full breakdown, see [Supported agent types](/docs/new-relic-control/agent-control/agent-types).

## Architecture

Agent Control uses a declarative approach to agent management. It treats the remote configuration received from Fleet Control as the desired state of your instrumentation, continuously ensuring that what's defined in Fleet Control is what's actually running.

### Kubernetes: Flux as the declarative engine

On Kubernetes, Agent Control acts as a translator between Fleet Control (the desired state) and Flux (the delivery mechanism):

1. Agent Control receives the desired state from Fleet Control via OpAMP.
2. Agent Control creates or updates Flux `HelmRelease` and `HelmRepository` Custom Resources.
3. Flux controllers pull the corresponding Helm charts and deploy or upgrade the agent pods.
4. Agent pods report health, which Agent Control surfaces back to Fleet Control.

This architecture means Agent Control on Kubernetes does not need to understand each agent's internal deployment mechanics. Flux handles that. Agent Control only needs to know how to express the desired state as Flux resources.

### Linux and Windows: Host-based management

On Linux and Windows, Agent Control operates without Kubernetes or Flux. The supervisor runs as a system service and manages agents as child processes:

1. Agent Control receives the desired state from Fleet Control via OpAMP.
2. Agent Control downloads the agent package from New Relic's OCI-compliant package registry.
3. Agent Control installs and starts the agent as a managed process, writing the rendered configuration to disk.
4. Agent Control monitors the agent's health and reports status back to Fleet Control.

## Agent Control permissions

Agent Control is designed to perform powerful lifecycle actions within your environment. Understanding what it needs and why is important before deploying.

### Kubernetes

Agent Control and Flux have separate, well-scoped permission sets:

| Component | What it can do | Why |
| :--- | :--- | :--- |
| **Agent Control** | Create, read, update, delete `HelmRelease` and `HelmRepository` Flux CRDs | Instructs Flux what agents to deploy, without needing cluster-admin rights |
| **Flux** | Create `Deployments`, `DaemonSets`, `Services`, `ConfigMaps`, `Secrets`, and other Kubernetes resources | Deploys and manages the actual agent pods on behalf of Agent Control |

Flux requires elevated permissions (typically `cluster-admin`) because it needs to create and update arbitrary Kubernetes resources on behalf of the user. If your security policy requires a least-privilege Flux setup, see [Custom Flux deployment configuration](/docs/new-relic-control/agent-control/deployment-configurations/#custom-flux) for a `ClusterRole` example.

### Linux and Windows hosts

On Linux and Windows, Agent Control runs as root or LocalSystem because it needs to:

- **Install agents:** Copy binaries and write configuration files to system directories.
- **Manage processes:** Start, stop, and restart agent services via `systemd` or the Windows Service Manager.
- **Access system data:** Read performance metrics, logs, and inventory needed for health reporting.

Elevated privileges are used strictly for these declared lifecycle tasks. Agent Control follows a declarative model: it reads the desired state and only takes the actions needed to reach it.

### Agent-specific permissions

Each agent type requires additional permissions beyond what Agent Control itself needs. An agent collecting Kubernetes API metrics needs more access than an agent reading log files. Agent Control is designed to request only the minimum permissions required for the specific agents you deploy.

For a full breakdown, see [Supported agent types](/docs/new-relic-control/agent-control/agent-types).

## Requirements and compatibility

### Kubernetes

| Requirement | Details |
| :--- | :--- |
| Helm | Version 3 or higher |
| Kubernetes | Last three minor releases; Minikube, Kind, Amazon EKS, Azure AKS, Google GKE |
| New Relic license key | Required to report telemetry |
| Auth Domain Manager role | Required to connect Agent Control to Fleet Control |

<Callout variant="caution" title="Existing instrumentation">
  If your Kubernetes cluster is already instrumented with New Relic, uninstall the existing instrumentation before installing Agent Control. See [Migrate existing instrumentation](/docs/new-relic-control/agent-control/reinstrumentation).
</Callout>

<Callout variant="caution">
  Installing multiple instances of Agent Control on the same cluster is not supported.
</Callout>

For Kubernetes agent-specific requirements, see:
- [Kubernetes integration: compatibility and requirements](/docs/kubernetes-pixie/kubernetes-integration/get-started/kubernetes-integration-compatibility-requirements)
- [OpenTelemetry for Kubernetes](/docs/kubernetes-pixie/kubernetes-integration/installation/k8s-otel)

### Linux hosts

| Requirement | Details |
| :--- | :--- |
| Processor architectures | x86_64, arm64 |
| Supported OS | Amazon Linux 2 / 2023, CentOS 8+, Debian 11+, RHEL 7+, Oracle Linux 8+, SLES 12.5 / 15.x, Ubuntu 16.04+ (LTS only) |
| Not yet supported | macOS, Docker (containerized) |

To check your OS version:
```bash
cat /etc/os-release
```

### Windows hosts

| Requirement | Details |
| :--- | :--- |
| Processor architectures | x86_64 |
| Supported OS | Windows Server 2016+, Windows 10+ |
| Privileges | Administrator (required for install and runtime) |
| PowerShell | Version 5.0 or higher |
| Port | 51200 must be available (health endpoint) |
| Network | Outbound HTTPS (port 443) to New Relic services |

<Callout variant="important" title="Windows support limitations">
  **Supported agents:** Windows hosts currently support only the **New Relic Infrastructure Agent** and **NRDOT** (OpenTelemetry Collector, experimental). Fluent Bit, Prometheus, eBPF, and APM agents are not supported.

  **Minimum agent versions:** Infrastructure Agent 1.71.0+, NRDOT 1.5.0+. Older versions will fail to deploy.

  **Fleet type:** You must use a fleet of type **"Host - Windows"**. Using other fleet types causes failures.

  **Log collection:** Use the Infrastructure Agent's built-in Fluent Bit integration (`config_logging`) for log forwarding on Windows.
</Callout>

To check your Windows version:
```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsHardwareAbstractionLayer
```
